DOCX accessibility checker: what Microsoft misses

By Preflight A11y · 29 October 2026 · 7 minute read

Microsoft's Accessibility Checker is the first tool most course teams open. It is free, built into Word, and it catches several real problems before a document is published. But it is a pane inside Word, not an audit report, and it cannot tell you whether the alt text actually makes sense.

This guide covers what the built-in checker does well, the DOCX checks that still need a person or a second tool, and how to produce a report you can hand to a client or an instructional designer.

Short version: use the Microsoft checker as a first pass, then verify structure, reading order, alt-text quality, table headers, links, and tracked changes. A clean automated report is not proof of WCAG conformance.

What the built-in checker is good at

Microsoft documents the Accessibility Checker for Word, PowerPoint, Excel, Outlook, and OneNote. In Word it flags items such as missing alternative text, missing table header rows, merged or split cells, and some heading issues, with a “Recommended Actions” list. For a quick pass before sharing a draft, that is useful.

Its limits are structural:

  • It is a pane, not a portfolio report. You cannot hand a client a consistent PDF/HTML report with severity, WCAG references, and a remediation plan.
  • It cannot judge meaning. Alt text like “image1.png” or “graphic” may pass a presence check but fail a screen-reader user.
  • Reading order is hard to verify. Floating text boxes can be read in a different order than they appear.
  • It does not test the experience. Screen-reader pronunciation, keyboard order, and whether a table makes sense are manual checks.

Seven DOCX checks to do after the built-in checker

1. Set a real document title

Go to File → Info → Properties → Title. Use a short, descriptive title, not the file name. A title helps screen-reader users and navigation tools identify the document. The WCAG reference is 2.4.2 Page Titled.

2. Set the document language

Use Review → Language → Set Proofing Language and set the default for the document. If the document is mostly English but contains a French quotation, mark the quotation separately. The reference is 3.1.1 Language of Page.

3. Use real heading styles, in order

Select the document title and apply Heading 1; use Heading 2 for sections and Heading 3 for subsections. Do not use bold body text as a fake heading. A screen-reader user can jump by heading; a bold paragraph is invisible to that navigation. See 1.3.1 Info and Relationships.

4. Write alt text for purpose, not pixels

Right-click the image → Edit Alt Text. Describe what the image communicates in this context, in one or two sentences. A decorative divider should be marked decorative, not described. A chart needs the takeaway (“Enrollment rose 18% from 2024 to 2025”), not “chart”. The reference is 1.1.1 Non-text Content.

5. Give data tables a header row and repeat it

Select the header row → Table Layout → Repeat Header Rows. Keep the table simple; merged cells make it harder for screen readers to associate values with headers. If the table is only for layout, use a real layout, not a data table.

6. Make link text descriptive

“Click here” and “read more” fail when a screen-reader user navigates link-to-link. Use the destination or action: “Download the grading rubric (PDF)”. The reference is 2.4.4 Link Purpose (In Context).

7. Check text boxes, tracked changes, and comments

Floating text boxes can break reading order. Accept or reject tracked changes before publishing, and delete internal comments. Both can expose draft content or make the reading experience inconsistent.
